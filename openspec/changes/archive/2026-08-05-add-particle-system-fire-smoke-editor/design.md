## Context

`fury3d` has a scene graph (`SceneNode` + `Component`), an asset graph (`EntityManager` keyed by name → `Mesh` / `Material` / `Texture` / `Shader`), a deferred Lambert / HDR-PBR rendering path, an ImGui editor (`furye`), and a CLI surface (`fury`). There is no particle subsystem. The shipped `examples/Projects/outdoor/outdoor_water.bin` scene has a wood pile with a `Light` (point) parented to it but no animated geometry to read as fire.

The closest analogues in the codebase are:

- `MeshRender` (`engine/Fury/MeshRender.{h,cpp}`) — a per-instance `Component` that owns material/mesh refs, lives on a `SceneNode`, and is walked by the render pass. Particle components will follow the same shape.
- `Animator` (`engine/Fury/AnimationPlayer.{h,cpp}`) — a CPU-side stateful component ticked each frame; its module-style split (`AnimationClip` + `AnimationChannel`) is the inspiration for `ParticleModules`.
- The mesh editor's 3D preview (`engine/Fury/Editor/EditorAssetWindows.cpp` `RenderMeshPreview` ~line 800) — owns an `OrbitState`, a `PreviewRT` FBO, a ground grid, and an AABB wireframe. The particle editor needs the same shape.

Constraints carried in from prior memory: linear gbuffer depth, transparent-after-opaque ordering, GL state hygiene between passes, no silent BindTexture mismatches (rebind `GL_TEXTURE_2D` per shader), meter-scale tuning. The HDR PBR pipeline already in place is the rendering target; the particle shader slots into it as a transparent pass.

Stakeholders: engine author (uses the new API to build scenes), artist (uses the editor to author emitters), the outdoor demo (visual deliverable: fire on the wood pile).

## Goals / Non-Goals

**Goals:**

1. A Unity-style `ParticleSystem` (simulation, a project asset in the scene's `EntityManager`) + `ParticleRenderer` (component on a `SceneNode`, references the system by name) pair that updates on the CPU, renders as billboard quads, and integrates with the existing transparent pass.
2. A module-driven authoring surface (Emission, Shape, Velocity, ColorOverLifetime, SizeOverLifetime, RotationOverLifetime, Renderer) so emitters are data-driven, not code-driven.
3. Two emitters — fire + smoke — added to `outdoor_water.bin` above the lit wood pile, with textures generated by Python noise.
4. A per-asset particle editor in `furye` that shares the mesh editor's 3D preview infrastructure (orbit camera, FBO, ground grid, AABB wireframe) via a new `Editor3DPreview` helper.
5. Self-verification: launch `fury` against the updated scene, capture `screenshots/outdoor_fire_smoke.png`; launch `furye`, open the particle editor, confirm preview updates live.

**Non-Goals:**

- GPU compute particles, mesh particles, trail particles, sub-emitters, particle collision/forces, soft-particle depth-fade.
- Multi-threaded particle update (single-threaded CPU update is fine for ≤ a few thousand particles; this change targets hundreds per emitter).
- A particle-instancing render path (one draw call per emitter with the dynamic VAO is enough; per-particle batching comes later if profiling demands).
- Authoring tools for emitter templates / presets library (one emitter per asset, no nested prefabs).
- Hot-reloading particle assets in the editor (save → restart pattern, matching the rest of the asset editor flow).

## Decisions

### Decision 1 — Asset + renderer pair, not one monolithic component

`ParticleSystem` owns simulation state and the `Update(dt)` walker; `ParticleRenderer` owns the dynamic VAO and the `Draw()` walker. Mirrors Unity's split and lets a user disable rendering (e.g. for offscreen logic-driven emitters) without losing the simulation, and lets the existing render pass add the renderer to its transparent queue without teaching it about the simulation.

**As implemented (2026-07-31, supersedes the original "component pair" framing):** `ParticleSystem` is a **project asset** registered in the active Scene's `EntityManager` (alongside `Mesh` / `Material` / `Texture` / `AnimationClip`), referenced **by name** from the `ParticleRenderer` component — not itself a `Component`. Consequences that follow from the asset model: content-browser tile + asset-picker row + `Importer.MergeInto` transfer all treat it like a mesh/material; scenes serialize it in a top-level `particleSystems` array; several `ParticleRenderer`s on different nodes can share one system asset. Each `ParticleSystem` instance ticks via its own `Engine::OnUpdate` subscription (the `Animator` pattern: subscribe in `Create`, unsubscribe in dtor) rather than a `Scene::Update` walk — the editor preview can also drive `Update(dt)` manually, gated by `SetExternallyDriven` while a particle editor window has the system open.

**Alternatives considered**: single `ParticleComponent` (simpler today, harder to extend; rejected — adding sub-emitters or simulation-without-rendering would force a rewrite later). ParticleSystem-as-Component (the original text; rejected at implementation time — components die with their node and can't be picked/rebound/duplicated as assets; the EntityManager model already solves lifetime, serialization, and editor browsing).

### Decision 2 — CPU simulation, dynamic VAO

Particles live in a `std::vector<Particle>` on `ParticleSystem`; the renderer copies the live positions into a `Mesh`-backed dynamic VBO each frame and draws with one `glDrawElements`. The cap is small (hundreds per emitter, ~2 emitters per scene in v1), so the per-frame upload is cheap and we get to reuse the existing `Shader::BindMesh` path.

**Alternatives considered**: shader-side simulation via transform feedback (rejected — engine's GL baseline doesn't assume 4.x features; would require a fallback). GPU compute via SSBO (rejected — out of scope per Non-Goals; deferred until profiling forces it).

### Decision 3 — Module structs, not class hierarchies

`EmissionModule`, `ShapeModule`, `VelocityModule`, `ColorOverLifetimeModule`, `SizeOverLifetimeModule`, `RotationOverLifetimeModule`, `RendererModule` are plain structs with `Load/Save` and an `Apply(Particle&, float t01)` method. Mirrors Unity's `ParticleSystem.EmissionModule` etc. — easy to serialize, easy to edit, easy to extend. Each struct lives in `ParticleModules.h`.

**Alternatives considered**: class hierarchy (`BaseModule` + derived) (rejected — overkill for data-driven authoring; reflection costs in `EditorReflect` would dominate).

### Decision 4 — Reuse `Material` for the particle texture

`ParticleRenderer::SetMaterial(material)` binds a `Material` whose `DIFFUSE_TEXTURE` slot holds the smoke/fire PNG. The new `ParticleShader` reads that slot. No new texture-binding path. Materials already round-trip through save/load, are already picked by `EditorAssetPicker`, and already feed the inspector pattern.

**Alternatives considered**: a new `ParticleMaterial` class (rejected — duplicates the existing texture-binding code; would require teaching every editor panel about a second material kind).

### Decision 5 — `Editor3DPreview` helper extracted from `RenderMeshPreview`

`EditorAssetWindows.cpp`'s `OrbitState`, `PreviewRT`, ground grid, AABB wireframe, and camera-projection helpers move into `engine/Fury/Editor/Editor3DPreview.{h,cpp}` with a `Render3DPreview(scene_or_callable, popup_id, size, aabb_or_callable)` signature. `RenderMeshPreview` and the new `RenderParticlePreview` both call into it. Single source of truth for the orbit camera, the ground grid, and the AABB wireframe — future editors (animation preview, material preview) join later.

**Alternatives considered**: a `IEditorPreview` interface (rejected — overkill for two callers; the helper is a free function, not a virtual). Inline copy in the particle window (rejected — exactly the duplication we're trying to avoid).

### Decision 6 — Noise textures, committed as static assets (generator not committed)

`examples/Projects/outdoor/fire.png` and `examples/Projects/outdoor/smoke.png` are 256×256 RGBA PNGs (radial gradient + FBM warp for fire; radial alpha + FBM-eroded edge for smoke), committed as static assets in the outdoor project's own directory — texture paths resolve as `workingDir + path` string concat, so a shared `Resource/Particle/` home would require the repo's first `../../`-traversal texture path (untested against save-side relocation), and the repo direction is per-project self-contained assets.

**Generator removed from the change (user directive 2026-07-31):** the original plan committed `engine/Tools/gen_particle_textures.py` for reproducibility; the user ruled texture tooling temporary — don't commit it. The PNGs are plain static assets now; re-authoring them means writing a new throwaway noise script (recipes: fire = radial white→yellow→orange→red gradient with 4-octave value-noise FBM coordinate warp; smoke = 0.55 gray premultiplied into domain-warped FBM density with a threshold for wispy holes + radial edge mask — the original radial-falloff version read as a fake smooth blob and was regenerated 2026-08-03).

**Algorithm**:
- Fire: 256×256 RGBA. Build a radial gradient (white center → yellow → orange → red → alpha 0), perturb sample coordinates by 2D FBM (4 octaves, value noise built from a seeded hash), saturate so additive blending stays bright. Result: a non-tiling warm blob with visible internal "wisps".
- Smoke: 256×256 RGBA premultiplied. Build a radial alpha falloff, fill RGB with cool gray (~0.55), perturb with FBM and erode so the edges look fluffy. Result: a non-tiling soft puff.

**Alternatives considered**: hand-painted PSDs (rejected — defeats "generated with Python noise"; the whole point is reproducibility + zero art deps). Perlin via `noise` PyPI (rejected — adds an install step; value-noise from a seeded hash is ~40 lines and gives identical results).

### Decision 7 — Editor preview driven by manual preview-time, not scene clock

The particle editor's preview runs the simulation in-place at the user-controlled time (slider + Play/Pause), independent of the editor's wall clock. Lets the author scrub the size-over-lifetime curve and see exactly what frame 0.7 looks like. Mirrors Unity's Particle System window.

**Alternatives considered**: tie preview to the editor scene clock (rejected — would couple the editor preview to whatever else is playing in the scene; the slider is the universal artist tool).

## Risks / Trade-offs

- **[Risk]** Per-frame VBO upload stalls on large emitters → **Mitigation**: cap emitter count at `g_MaxParticlesPerEmitter = 4096` for v1, log a warning if the user exceeds it, document the cap in the editor's module inspector. If profiling later shows the cap is too low, swap to `glBufferSubData` with double-buffered VBOs (one write, one draw) — a localized change inside `ParticleRenderer`.
- **[Risk]** Particle sort order against the rest of the transparent pass is wrong (smoke in front of fire when it should be behind) → **Mitigation**: the existing transparent pass already sorts by camera distance; particles participate in that sort. Document the rule (single emitter = no sort cost; multiple emitters in the same draw pass are sorted by emitter center, not per-particle) and revisit if artists file z-fighting tickets.
- **[Risk]** `Material::DIFFUSE_TEXTURE` slot reused for the particle texture breaks HDR-PBR material expectations → **Mitigation**: the particle shader is its own `Shader` (a new `ShaderType::PARTICLE`); the material's PBR slots (`METALLIC_ROUGHNESS_TEXTURE`, `OCCLUSION_TEXTURE`) are unused but the same `Material` instance can be shared with regular meshes if the artist wants (the PBR shader ignores them).
- **[Risk]** Editor3DPreview extraction regresses the mesh editor's preview (camera framing, ground grid scale, AABB wireframe line widths) → **Mitigation**: the extraction keeps the existing tunables verbatim (`initialDistance = radius * 0.6 / (tan(fov/2) * min(1, aspect))`, `grid_extent = radius * 2`, `aabbVerts` byte-identical). The mesh editor's smoke test (open outdoor scene → mesh editor → verify framing on a known mesh) is added to the task list as a regression check.
- **[Risk]** Re-saving `outdoor_water.bin` introduces silent scene-shape drift if the importer normalizes the node graph differently → **Mitigation**: edit the existing `.json` sibling (`outdoor_water.json` if it exists; otherwise re-author via `fury save` after a `fury load` round-trip) and re-encode with `FileUtil::SaveCompressedFile`, then diff the new `.bin` against the previous git version for unexpected node additions. Any drift goes in the PR description.
- **[Risk]** Generated PNGs visually clash with the existing scene's lighting → **Mitigation**: tune the fire PNG's gradient stops against the existing point light's color/intensity in `outdoor_water.json`. If the fire looks washed-out, raise the PNG's core saturation; if it disappears, raise the smoke PNG's base alpha. Both are one-line edits to `gen_particle_textures.py` plus a re-run.
- **[Risk]** Outdoor scene's wood-pile world position differs between `.bin` and the re-saved form → **Mitigation**: read the existing `outdoor_water.json` (or the live scene via `fury info`) for the wood pile node's `pos` before adding the emitter; carry that `pos` through verbatim.

## Migration Plan

1. Land the engine sources (ParticleSystem, ParticleRenderer, ParticleModules, EditorParticleWindow, Editor3DPreview). Build, run existing smoke tests, confirm no regression.
2. Refactor `EditorAssetWindows.cpp`'s `RenderMeshPreview` to delegate to `Editor3DPreview`. Confirm the mesh editor's preview still frames the same meshes correctly (visual check + screenshot diff against the prior state).
3. Run the Python texture generator; commit the two PNGs.
4. Author `ParticleEmitter` nodes in the outdoor scene's working directory; re-save `outdoor_water.bin`.
5. Self-verify: launch `fury` against the scene, screenshot `screenshots/outdoor_fire_smoke.png`. Launch `furye`, open the particle editor, scrub the size curve, screenshot.
6. Rollback is per-commit — the change is self-contained, and the outdoor scene's `.bin` is the only scene asset that changes. `git revert` of the commit restores the prior `outdoor_water.bin` and removes the new sources in one motion.

## Open Questions

- Should the existing `Material::DIFFUSE_TEXTURE` slot be reused for particles, or should a dedicated `ParticleRenderer::SetTexture()` overload exist for users who want particles without authoring a Material? **Default decision for v1**: Material reuse (matches Unity's pattern of `ParticleSystemRenderer.material`). If a user needs a quick-path, an overload is a 5-line addition.
- Does the outdoor scene's wood-pile node use a parent transform that would push the emitter offset in a non-obvious direction? **Resolved at apply time** by reading the live scene graph first.
- The CLI's `fury info` output currently lists meshes / materials / animations / joints; should it also list `ParticleEmitter`s? **Default decision for v1**: yes, add a `particles` line; if the count grows past a threshold the info dump becomes noisy, but for one or two emitters it's the right level of detail.
