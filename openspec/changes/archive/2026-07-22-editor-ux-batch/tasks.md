## 16. Unify normal-gen / mesh-weld through MeshUtil::OptimizeMesh (user request 2026-07-21)

**Finding (2026-07-21):** `MeshUtil::OptimizeMesh` (MeshUtil.cpp:490) **already implements** the assimp `JoinVerticesProcess` optimization — a fixed non-axis-aligned `dividePlane(0.6, 0.7, -0.4)`, each vertex's signed distance to it cached in `VtxEntry`, entries sorted by distance so `FindNeighbors(pos, radius)` scans only the `[dist-radius, dist+radius]` slice instead of the full O(n²) all-pairs compare (see the file header ref to `code/JoinVerticesProcess.cpp`). It does epsilon-tolerant weld + dedup/reindex. **But it is only called on engine-generated primitives** (sphere at MeshUtil.cpp:320, cone/cylinder at :422) and via the `MeshUtil.OptimizeMesh` Lua binding. `MeshUtil::CalculateNormal` (MeshUtil.cpp:824) is likewise Lua-only — never auto-invoked. **The glTF/FBX import path does its own thing:** `GltfImporter.cpp:588-665` hand-rolls normal generation with an *exact-float* `unordered_map<PosKey>` weld (bit-identical positions only, no epsilon) purely to group normals for smooth accumulation — it never dedups/reindexes the vertex buffer and never calls MeshUtil. So imported meshes keep exporter-split duplicate vertices, and the two weld implementations have diverged.

## 17. Scene save float-precision bug (user report 2026-07-21)

**Symptom:** Open `tank.fbx` (metre-scale positions ~0.00017) → Save As `.json`/`.bin` → load the saved file → tank geometry is mangled (wheels non-round, tracks warped). The mesh inspector reports identical vert/index counts, so the data structure round-trips — only the rendering is wrong. Reverting `scene.bin` to git HEAD (pre-metre-scale, cm-scale ~20-unit positions) renders fine.

**Root cause:** `FileUtil::SaveFile` / `SaveCompressedFile` / `SaveByExtension` / `SerializeToString` all defaulted `maxDecimalPlaces = 5`, passed to RapidJSON's `PrettyWriter::SetMaxDecimalPlaces(5)`. This truncates floats to **5 digits after the decimal point** — magnitude-dependent, not significant-digit-dependent. For the tank's metre-scale positions (`0.00017294308…`), 5 decimal places leaves only **1-2 significant digits** (`0.00017`), a 1.7-3.5% per-position error that visibly warps the geometry. For the old cm-scale scenes (`20.12345…`), 5 places = 7 significant digits — fine. The bug is pre-existing (`maxDecimalPlaces = 5` predates this change), but only triggered now because the auto-scale change (§3) made the user open `tank.fbx` — the first metre-scale asset saved through this path.

**Investigation path (for the record):** OptimizeMesh was ruled out first (user tested with the flag off — still mangled). Smooth-normal-gen was ruled out second (added a `FURYW` log in `TranslateMesh` + the `!has_normals` block; `fury convert fbx tank.fbx` confirmed tank.fbx ships authored NORMAL accessors, so the normal-gen block never runs — the entire `TranslateMesh` change set is a no-op for this asset). The mesh data round-tripped (identical counts) but the rendering differed, pointing at either GL-buffer state or serialization precision. Comparing `fury info` on old-vs-new `scene.bin` showed the AABBs differed by exactly 100× (auto-scale), but the user confirmed the mangle persists even unscaled. The user's hypothesis — "limited floating point precision in the saved json" — was confirmed by grepping for `SetMaxDecimalPlaces` and finding the `= 5` default in `FileUtil.h`.

- [x] 17.1 **Fix:** Changed the default `maxDecimalPlaces` from `5` to `324` (RapidJSON's `kDefaultMaxDecimalPlaces` = full round-trip precision) in `FileUtil.h` for all four save functions. Added a comment explaining the magnitude-dependence gotcha. Verified: `fury convert fbx tank.fbx /tmp/tank_fixed.json` now writes positions like `0.0001729430805426091` (16 sig digits) instead of `0.00017` (2 sig digits). User confirmed the round-tripped tank renders correctly.

## 18. Import flag persistence (user request 2026-07-21)

The Settings → Import flags (`auto_default_sun`, `auto_scale_detect`, `normals_smooth`, `optimize_mesh`) are hardcoded to `true` in `Editor.lua::on_init` every launch. Toggling them in the UI lasts only for the session — a restart resets them. They should persist across sessions like the other editor preferences (gizmo mode, snap settings, grid toggle) that are saved to `imgui.ini` via the FuryEditor settings handler.
